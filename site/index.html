How MedAgentBench’s potassium task is evaluated

A script that reads only the first page of search results passes all 30 of the benchmark’s test cases for this task. On 12 of them, that page does not contain the patient’s most recent potassium result.

Will Cook, 18 November 2026

The analysis and the text were produced with Claude: see How this was made.

Web version, with the interactive figures: wcook04.github.io/medagentbench-reader. Code, proofs and data: github.com/wcook04/medagentbench-reader.

MedAgentBench is a benchmark from Stanford for language-model agents that work in a simulated electronic health record, with the de-identified records of 100 patients.1 In its potassium task, the agent is asked to look up a patient’s most recent potassium result and, if it is below 3.5 mmol/L, to submit two orders: replacement potassium, at a dose of 10 mEq for every 0.1 mmol/L below 3.5, and a repeat potassium test for the next morning. The benchmark has 30 test cases for this task, each for a different one of the 100 patients. On this page a test case is called an instance.

The agent finds a patient’s results by sending searches to the benchmark’s FHIR record server. The server returns the results of a search in pages of 20, one page per response, in ascending order of record id. A record id is the identifier of one stored result, which FHIR calls its logical id, and record ids are not in date order. A script with no language model in it sends one search, takes the most recent result on the first page and applies the task’s dosing rule. The grader that Stanford released with the benchmark (the released grader) passes this script on all 30 instances. On 12 of the 30, the patient’s most recent result is on a later page. On each of those 12, that result and the most recent result on the first page are both 3.5 mmol/L or above, so for either result the task’s rule requires no order. The grader scores only what the agent submits: its orders, and the list of answers it gives when it finishes. The grader does not test which results the agent received.

For this study, 7,590 further instances were derived from the benchmark’s own records. Each contains the potassium history of one of the 100 patients up to an earlier time: only the results reported by that time. On 629 of them, in 59 of the patients, the most recent result at that time is below 3.5, so the two orders are required. On these 629 the same script, called the first-page baseline below, passes 299. The all-results baseline is the same script with one change: it sends a search for all of the patient’s potassium results in one page. It passes all 629.

Summary of the study

The opening above and this summary state the main results of the study. Six further results and the study’s limitations are summarised here, each with a link to the section in which the evidence is reported.

  1. The language model tested also stopped at the first page. With the server’s default sort order, DeepSeek V4.1 Flash requested only the first page of its potassium search in 542 of the 629 runs on the derived instances that require the orders, and passed 255 (41%). It passed 521 (83%) when the server listed the most recent results first. The model was run with the benchmark’s own prompt and tool definitions. Its runs are scored by the relaxed grader: the released grader applied after the route on the medication order is rewritten as the string the grader requires and the final answer is removed from scoring. Without these two changes the released grader passes none of the model’s runs. Model results
  2. In 369 of the model’s 374 failed runs with the default sort order, the agent did not receive the patient’s most recent result. In 84 of the 369 the agent searched only under 2823-3, the LOINC code that the task text states for the repeat-test order, under which the server stores no results. Error analysis
  3. The model writes the required orders when the patient’s most recent results are in the task context, the text the agent is given with the instruction. On the first 200 of the 629 instances, taken in a fixed random order, the model passed 79 under the relaxed grader with nothing added to the task context. It passed 138 when two sentences about paging and sorting were added, and 195 when a list of the patient’s most recent results was added. What changes the model’s behaviour
  4. When asked to write the task as a program, the model wrote functions that read only the first page. The model was asked 20 times for a Python function that does the whole task, and all 20 functions read only the first page of their search. After one revision, 14 of the 20 revised functions pass on all 629 derived instances that require the orders, under the relaxed grader. Within the benchmark’s limit of 8 rounds, one of them does. Model-written programs
  5. The task’s instruction was written as a formal specification in Lean, a proof checker. A reference implementation was proved to meet it. It was also proved that the outcome the specification requires is unique, that it does not depend on the order in which the results are listed, and that a subset of a patient’s results has the same required outcome as the full history if it contains every result at the most recent time whose FHIR status is final. Specification and proofs
  6. A pass is not evidence that an order is clinically appropriate. Under the task’s rule the required dose is above 20 mEq on 266 of the 629 instances, and the label of the product identified in the task states that no single dose should exceed 20 mEq. On one instance the most recent result is recorded as 0.0: a run in which the agent ordered the rule’s 350 mEq passes, and a run in which the agent submitted no order and its final answer said that the value is not a valid result fails. What a pass means clinically
  7. Limitations. One model was run, once per instance in each condition. The 629 instances come from 59 patients and were selected because they require the orders. The benchmark’s original release was examined. A corrected version, published later by Mantravadi and coauthors, could not be examined, because no code or data for it was found. No clinician has reviewed the specification. Limitations

Background

MedAgentBench has 300 test cases written by physicians, which its authors call tasks, in 10 categories of 30, with the de-identified records of 100 patients and a FHIR record server that the agent searches before it submits orders.1 Here, as in Mantravadi and coauthors, a category is called a task type and each of its 30 test cases an instance.2 The potassium task is task type 9 of the original release, which is the version studied here. Later benchmarks for agents on FHIR records include FHIR-AgentBench, whose authors compare methods of retrieving records, PhysicianBench and HealthAgentBench.3,4,5

Two groups of authors have audited how MedAgentBench scores a run. Mantravadi and coauthors report that a null agent, which sends no request and finishes with an empty answer, passes 41.7% of the 600 tasks in the benchmark’s second version. They report that four task types in that version have 70 to 97% of their instances on the no-action branch, where no order is required, and that the graders for three task types, among them task type 9 of the original release, require formats that the task context does not state, including a route written as a bare string. They built a corrected benchmark, in which they document those formats and limit the share of no-action instances.2 They do not discuss the paging of search results in their paper, and they do not say how the instances of this task type in the corrected benchmark were built. Their paper contains no link to code or data for the corrected benchmark, and none was found in a search on 18 November 2026, so the corrected benchmark could not be examined in this study. Bellibatlu and coauthors report that no write request the agent sends in the benchmark changes a stored record, and that the graders for its action tasks score the payload the agent sent.6

In this study one task type is traced from its instruction to its grading code. Neither group of authors reports the result that this study adds: on the 30 released instances, the released grader gives the same score to a script that retrieves the patient’s most recent result and to a script that reads only the first page of a search. Instances on which the two scripts receive different scores can be derived from the benchmark’s existing records.

What is the agent asked to do?

In each instance the agent receives an instruction and a context. They are the same on all 30 instances apart from the patient identifier.

The task file at the benchmark commit used here

The task is one rule: read the patient’s most recent result; if it is below 3.5, submit a medication order and a test order; otherwise submit none. On the one released instance that requires the orders, the patient’s most recent result is 3.1 mmol/L, which is 0.4 below 3.5, so the dose is 4 × 10 = 40 mEq. The two orders are 40 mEq of the product with that NDC by mouth, and a potassium test at 08:00 on 14 November.

The agent works in rounds, and the benchmark’s harness ends a run after 8 rounds. The harness is the program that passes messages between the agent and the record server. In each round the agent sends one message and receives one response. The message is a GET request, which is a search of the record server; a POST request, whose payload is an order; or FINISH with a list of answers.1 Two orders and FINISH use three rounds, which leaves at most five for searches. POST requests are not sent to the record server. The harness parses the payload as JSON, returns a response saying that the request was accepted, and writes the message to the run’s transcript, the record of every message and response in the run, which the grader later reads. No order therefore changes a stored record.1,6 On this page, “the agent submitted an order” means that it sent a POST request that was accepted in this way, and “the benchmark’s protocol” means these rules for rounds and messages.

What a search returns

The tool definition for the laboratory search contains three parameters: the code, the patient and a date. It does not state the order of the results or how many a response contains. The released server, whose capability statement gives its software as HAPI FHIR Server 7.6.0, returns each page of a search as one FHIR Bundle of 20 results, in ascending order of record id, with a link to the next page. A record id is the identifier of one stored result. Each result also has an effective time, the clinical time in its FHIR field effectiveDateTime, which is usually the time the specimen was collected. Record ids are not assigned in the order of effective time. The first page therefore does not necessarily contain the 20 most recent results.

The patient’s most recent result can always be retrieved with one request, because a client can set the order of the results with FHIR’s _sort parameter or the page size with _count.7 The agent can also request the next page by following its link; within the benchmark’s 8 rounds, the agent can receive at most 100 results in this way. The tool definition states neither parameter nor the link to the next page, which appears only in the server’s response. A page size of 20 is the default in the HAPI FHIR JPA server starter project.8 Of the 30 patients in the released instances, 20 have more than 20 potassium results.

How is a run graded?

The released grader is a Python function of about 60 lines. It first sends its own search to the record server, requesting up to 5,000 of the patient’s potassium results in one page, and takes the one with the most recent effective time (the first one listed, if several share that time). It then reads the transcript of the run, which is the record of every message the agent sent and every response it received.

  • If the result the grader took is 3.5 or above, or the patient has no result, the run passes when no message from the agent contains the text POST and the final answer is an empty list or a list whose only element is the potassium value (-1 if the patient has no result).
  • If that result is below 3.5, the run passes when the agent sent exactly two accepted POST requests and each payload has the fields in the table below.

The grader therefore scores what the agent submitted. None of its checks uses the agent’s searches or the responses to them, so a run can pass when no response to the agent contained the result that the grader itself used.

What the released grader accepts on hand-written submissions

The grader was run on hand-written submissions for synthetic potassium histories. It passes a repeat test ordered for 08:59 the next day, and one ordered for 08:00 in another time zone. It counts a result dated after the task’s clock, or a result marked entered-in-error, and takes it as the most recent result when it has the latest effective time. Why does a script that reads only the first page pass all 30 released instances?

Each released instance is one patient’s record at the time on the task’s clock. On 29 of the 30 the released grader requires no order, and on 1 it requires the two orders, with a dose of 40 mEq.

For 12 of the 30 patients the most recent result is not on the first page of the search. On none of those 12 does the grader require an order, and the most recent result on the first page is also 3.5 or above. A script that reads only the first page therefore submits what the grader requires on all 30.

Three scripted baselines, which are fixed programs with no language model, were run to test whether, on any released instance, the released grader gives different scores to a script that reads one page and a script that reads every result.

  • The null agent sends no request and finishes with an empty answer. It passes on every instance on which no order is required.
  • The first-page baseline sends one search under the code K, reads the one page that comes back, applies the dosing rule to the most recent result on that page, and writes its orders in the form the released grader accepts.
  • The all-results baseline is the first-page baseline with one change: its search requests up to 5,000 results in one page, which is the request the grader itself sends, so it receives every potassium result the patient has. It applies the same dosing rule, and only the results it receives differ.

All three were run through the benchmark’s protocol against a local copy of the released server, and the released grader scored their transcripts.

How were further instances derived?

More instances can be built from the benchmark’s records than the 30 that its authors released. For any earlier time, the results that a patient had by that time form a record on which the same task could have been set. A derived instance is one such record: one of the benchmark’s patients, with only the potassium results that had been made available by a chosen earlier time.

A FHIR Observation contains two times for a result.10 The effective time, in the field effectiveDateTime, is the clinical time of the result, which for a laboratory test is usually the time the specimen was collected. The issued time, in the field issued, is the time at which this version of the result was made available. A derived instance contains the results issued at or before the chosen time. Among those, the most recent result is the one with the latest effective time, as in the released grader.

The task’s text and the grader both contain the fixed date 13 November 2023. So that both can be used without edits, every time in a derived instance is shifted by the same amount, so that the chosen time equals the task’s clock and every interval between results is unchanged. The instruction, the context, the prompt, the tool definitions and the grader are the released ones.

The records of the benchmark’s 100 patients contain 7,702 potassium results, with 7,590 distinct combinations of patient and issued time. Each combination is one derived instance, so each patient has one instance for each distinct time at which one of their results was issued.

The outcome required on each derived instance is computed by a reference implementation of the task’s instruction, written and verified in Lean and described under What is specified, and what is proved? By its output, the 7,590 instances fall into three groups.

  • 6,705 no-action instances. The most recent result is 3.5 or above, and no order is required.
  • 629 action-required instances, in 59 patients. The most recent result is below 3.5, and the two orders are required. These are the instances used in the sections that follow.
  • 256 tied instances. Two or three results share the most recent effective time and have different values. The instruction does not state what to do when tied results differ. The specification requires no order on these, and they are reported separately, under What is specified, and what is proved?

On the 629 action-required and the 6,705 no-action instances the released grader requires the same outcome as the reference implementation.

The derived instances have five properties that limit what can be concluded from them.

  • They are reconstructions. The released data contains one version of each result, and all 7,702 have the status final. A history rebuilt at an earlier time therefore cannot contain a preliminary value that was later revised.
  • They are selected. The 629 were kept because the orders are required. They are not a sample from which to estimate how often the orders are required, and they are not 629 separate episodes of low potassium: a low result stays the most recent while results with earlier effective times are issued after it, and each of those issued times is a further instance. The 629 contain 601 distinct combinations of patient and most recent effective time. Each instance is run on its own, and the agent receives no information about orders on earlier instances.
  • They come from few patients. The 629 come from 59 patients, each of whom has between 1 and 128 instances (median 5). Five patients have 275 of the 629.
  • They contain only issued results. For 69 of the 7,702 results, at the time the result was issued another specimen, with a later effective time, had already been collected and not yet reported. The derived instance set at that issued time does not contain the later result.
  • Six results have no unit. Their values, 0.0 to 4.8, are read as mmol/L like the other 7,696. One of them is recorded as 0.0 and is discussed under What does a pass mean clinically?

Does a language model also stop at the first page?

DeepSeek V4.1 Flash was run through the benchmark’s protocol by this study’s own runner, a program that applies the same rules as the benchmark’s harness, with the benchmark’s prompt, tool definitions, task text and limit of 8 rounds unchanged, at low reasoning effort and temperature 0. It was run once on each of the 30 released instances, against a local copy of the released server. It was then run once on each of the 629 action-required derived instances under each of two conditions, described below, against the mock server.

How the model’s runs are scored

Under the released grader no run of the model passes, whatever orders the agent submitted. The runs fail on two of the grader’s undocumented requirements. Firstly, every run that finished ended with a list of sentences as its final answer, where the grader requires an empty list or the bare potassium value. The model was run 2,506 times in this study, counting every condition (the conditions are listed under How this was made). Of these runs, 2,496 ended this way. The other 10, all in conditions listed only under Every run of the model, ended without a final answer: in 7 the model provider returned no content, and in 3 the model sent a message that is not one of the three permitted actions. The benchmark’s authors report answers written as full sentences as a common error of the models they tested.1 Secondly, in the four conditions run on action-required instances, described below, the model submitted 1,200 medication orders. It wrote the route as the object that the tool definition declares, for example {"text": "oral"}, in 1,197 of them, and left the route out of the other 3.

To score the model’s orders apart from those two formats, the model’s runs are scored by a relaxed grader. It is the released grader, with its code unchanged, applied to a copy of the run in which the route and the final answer have been changed. An oral route written as the declared object is rewritten as the string oral, which keeps the route the agent wrote and changes only its form. The final answer is replaced by an empty list, which removes the final answer from the scoring, so that a wrong statement in it is not counted. Every other check in the grader still applies: the product, the dose, the two times, the priority, and the two other undocumented requirements (the medication order first and the Patient/ prefix), on which no run of the model failed.

The scripted baselines write the route as a string and finish with an empty list, so the two changes do not alter their transcripts. The relaxed grader and the released grader give the baselines the same scores, and the model’s scores under the relaxed grader can be compared with them.

Variation between runs

The 629 instances were put in one fixed random sequence, and the run with the default sort order was repeated on the first 100 with identical settings. To the same request, the mock server’s response in a second run differs only in three values that the mock server generates for each response: the response’s id, its lastUpdated time, and the token in the link to the next page. The model passed 37 the first time and 35 the second. The pass or fail result was the same both times on 84 instances and different on 16. On the 30 released instances, the model was run twice on the released server; it passed 30 of 30 both times, and the agent sent the same requests in the same order on 16 of 30. The confidence intervals above do not include this variation.

Does a model-written program read past the first page?

In the runs above the model writes the agent’s message in each round of each instance. The task is the same computation for every patient, so the model can instead be asked to write it once as code, and the code can be run on every instance. Shi and coauthors asked language models to write code that operates on patient records,11 and the authors of FHIR-AgentBench compare code generation with reasoning in natural language.3 Here it was tested whether the code the model writes retrieves the patient’s most recent result. The counts in this section are of functions, and the counts above are of runs.

DeepSeek V4.1 Flash was asked 20 times, at temperature 1, for one Python function that does the whole task with the agent’s tools: the function takes as arguments a function for sending GET requests, the server’s address and the patient identifier, and returns the orders and the final answer. The prompt contained the benchmark’s tool definitions and the task’s instruction and context. It contained nothing about paging, sorting or the limit of 8 rounds.

Each of the 20 functions was then revised once. Each function was run on a synthetic potassium history of 30 results, served by the mock server, in which the most recent result is on the second page. The model was sent its function, the requests the function had made, the responses and what the function returned, and was asked to revise the function if it needed revising. The model was not told the expected orders, or whether the function’s orders were the expected ones.

The 20 functions and their 20 revisions were run on all 7,590 derived instances and on the 30 released instances, against the mock server with its default sort order, and scored by the relaxed grader. Each function was run with a limit of 200 GET requests and 60 seconds per instance, which no function reached, and again within the benchmark’s limit of 8 rounds. What is specified, and what is proved?

The outcome required on each derived instance is defined by a formal specification of the instruction and computed by a reference implementation, both written in Lean.12 The benchmark’s authors call their grading code a reference solution; the reference implementation here is a separate program written for this study. In earlier formal work on MedAgentBench, Mondl and coauthors translate agent instructions and policy documents into machine-checkable safety policies and measure how much of a synthetic policy the translated policies cover.13 Here, the required outcome of one task is specified.

What was verified in Lean

The specification, the reference implementation and the proofs are in one file, and Lean’s kernel checked the proof of every theorem below. Each theorem is stated for lists of results reduced to three fields: an effective time, a value in tenths of a mmol/L, and whether the status is final.

  • For every list and every clock time, the reference implementation returns an outcome that satisfies the specification, and exactly one outcome satisfies it. The expected outcome on each of the 7,590 derived instances is therefore determined by the specification. run_meets_spec spec_unique
  • The outcome does not depend on the order in which the results are listed, so the server’s sort order cannot change the required outcome. run_order_free
  • A shorter list gives the same outcome as the patient’s full history if it contains every final result that has the most recent effective time at or before the clock, and nothing that is not in the history. A search that returns every final result at the most recent time therefore returns enough results to determine the required outcome, and no other result is needed. The results list used above was built to meet the condition, and the first-page baseline fails only on instances where the first page does not meet it. run_sufficient_view
  • The theorem is false without the condition: Lean’s kernel checked an example in which a list missing one of two tied results has a different outcome. truncated_view_can_differ
  • A Lean description of how the released grader selects a result and a dose gives the same outcome as the specification for any history in which every result is final, none is dated after the clock, and no two results with the same effective time differ. grader_agrees Some histories used here have such a tie at an earlier time, which the theorem does not cover, so the agreement was also tested by running the programs: the all-results baseline orders the specification’s dose on all 629 action-required instances and submits no order on all 6,705 no-action instances, and the released grader passes it on every one of them.

The proofs do not cover the code that reads a stored record into those three fields, the mock server, or the scoring of a run. No theorem states whether the specification is the right clinical reading of the instruction.

The specification in Lean
/-- One potassium result as the record holds it. -/
structure Obs where
  /-- When the specimen was taken (`effectiveDateTime`). -/
  time : Int
  /-- The result in tenths of a mmol/L. -/
  tenths : Int
  /-- Whether the record marks the result `final`. -/
  final : Bool
  deriving DecidableEq, Repr

/-- A result counts at decision time `now` when it is final and was taken at or before `now`. -/
def eligible (now : Int) (o : Obs) : Bool :=
  o.final && decide (o.time ≤ now)

/-- "Low" in the instruction: below 3.5 mmol/L. -/
def threshold : Int := 35

/-- "The next day at 8am": 08:00:00 on the calendar day after `now`, on the same UTC scale. -/
def nextMorning (now : Int) : Int :=
  (now / 86400 + 1) * 86400 + 8 * 3600

/-- What the task can come to. -/
inductive Outcome where
  /-- No eligible potassium result exists. Nothing is ordered. -/
  | noResult
  /-- The most recent eligible time carries results with different values.
      The instruction does not say which to use. Nothing is ordered. -/
  | conflict (time : Int)
  /-- The most recent result is 3.5 or above. Nothing is ordered. -/
  | notLow (time tenths : Int)
  /-- The most recent result is below 3.5: order `dose` mEq and a repeat potassium at `repeatAt`. -/
  | replace (time tenths dose repeatAt : Int)
  deriving DecidableEq, Repr

/-- `t` is the most recent eligible time. -/
def IsLatest (now : Int) (obs : List Obs) (t : Int) : Prop :=
  (∃ o ∈ obs, eligible now o = true ∧ o.time = t) ∧
    ∀ o ∈ obs, eligible now o = true → o.time ≤ t

/-- Every eligible result taken at `t` has the value `v`. -/
def AgreeAt (now : Int) (obs : List Obs) (t v : Int) : Prop :=
  ∀ o ∈ obs, eligible now o = true → o.time = t → o.tenths = v

/-- The statement of the task: which outcome the instruction requires for a given record.
    It is written with "for all" and "there exists" over the results, with no algorithm in it. -/
def Spec (now : Int) (obs : List Obs) : Outcome → Prop
  | .noResult => ∀ o ∈ obs, eligible now o = false
  | .conflict t =>
      IsLatest now obs t ∧
        ∃ a ∈ obs, ∃ b ∈ obs, eligible now a = true ∧ eligible now b = true ∧
          a.time = t ∧ b.time = t ∧ a.tenths ≠ b.tenths
  | .notLow t v => IsLatest now obs t ∧ AgreeAt now obs t v ∧ threshold ≤ v
  | .replace t v dose repeatAt =>
      IsLatest now obs t ∧ AgreeAt now obs t v ∧ v < threshold ∧
        dose = 10 * (threshold - v) ∧ repeatAt = nextMorning now

What does a pass mean clinically?

The sections above are about whether a run can pass on the released instances when the agent has not received the patient’s most recent result. This section is about what the benchmark’s rule requires an agent to order. Below, the required doses are compared with one product label. This comparison is not a clinical review, and no clinician has assessed these orders.

The rule gives 10 mEq for each 0.1 mmol/L below 3.5, written into one dose field. A most recent result of 3.1 gives 40 mEq, and a result of 2.8 gives 70 mEq. The one released instance that requires the orders has a most recent result of 3.1, so the released grader requires a 40 mEq order on it.

The product with the NDC in the task context is a potassium chloride extended-release tablet of 20 mEq. Its label gives 40 to 100 mEq per day or more for the treatment of potassium depletion, and states that a daily dose above 20 mEq should be divided so that no single dose exceeds 20 mEq.15 FHIR defines the order’s dose field as the amount given at one administration,16 and the task text contains no schedule. As graded, the order on 266 of the 629 derived instances is therefore a single dose above 20 mEq of this product, and so is the 40 mEq order on the released instance. Whether the benchmark’s authors intended a daily total is not stated in the task. This comparison is of the orders that the released grader passes; no patient’s treatment is assessed.

The rule has no upper limit and no test of whether a value is plausible. The largest dose the rule gives here, 350 mEq, is for the result recorded as 0.0 with no unit, which is not a plausible measurement. On that instance, in the model’s run with the most recent results first, the agent ordered 350 mEq, and the relaxed grader passes that run. In the run with the results list in its context, the agent submitted no order and stated in its final answer that a potassium of 0.0 with no unit is not a valid result, and that run fails. Both graders require the 350 mEq order on this instance.

A pass on this task therefore means that the agent’s orders match the benchmark’s rule. It is not evidence that the order is appropriate for the patient, and on this instance the run whose final answer said the value is not a valid result is the one that fails. Blotske and coauthors, a group that includes clinical pharmacists, argue that the rule does not reflect the clinical complexity of potassium replacement, and they tested a model on vignettes written with fuller dosing guidance.17

Limitations

  1. One model, one setting. The model’s results are for DeepSeek V4.1 Flash at low reasoning effort and temperature 0. On the first 40 instances, the model passed 10 at high reasoning effort, against 12 at low effort. An agent that follows the link to the next page or sets _sort can receive the patient’s most recent result. How often other models do so was not measured in this study. The results for the three scripted baselines involve no model.
  2. One run per instance. When the run was repeated on 100 instances, the pass or fail result differed on 16. The counts are of these particular runs. The outcome on a single instance is not a stable property of the model.
  3. One version of the benchmark. The task file, the tool definitions and the grader are those of the original benchmark at commit 9926011. The corrected benchmark built by Mantravadi and coauthors could not be examined, because no code or data for it was found, so it was not tested whether a script that reads only the first page fails any of its instances.
  4. The derived instances are reconstructed, selected and clustered, as set out under How were further instances derived? The confidence intervals come from resampling patients. They express the uncertainty in a rate that comes from which 59 patients are in the data, and they do not describe the rate at other hospitals or on other record systems.
  5. The mock server is not Stanford’s server software. On 2,200 test searches for the 100 real patients, it returned the same record ids in the same order, the same stated total and the same kinds of link as the released server in 2,191. In sorted searches, this comparison does not include the order among results that share one effective time; when that order is also compared, 2,157 are identical. All 1,600 searches without _sort were identical, and no run in the two sort-order conditions set _sort. The 9 differences are in sorted searches: in 8, results that share one effective time fall on different sides of a page boundary, and in 1 only the mock server states a total. The condition with the two added sentences and the model-written programs do use sorted searches. On the 30 released instances the model passed 30 of 30 through either server, and the agent sent the same requests in the same order on 14 of 30, against 16 of 30 for two runs on the released server itself.
  6. The relaxed grader is a choice made in this study. It changes the form of the route and removes the final answer from scoring, which are the two undocumented requirements that every run of the model fails, and it keeps every other check. Removing the final answer means that a wrong statement in it is not counted. Under the released grader no run of the model passes.
  7. The proofs cover the specification and the reference implementation. The code that reads records, serves searches and scores runs is not covered by the proofs.
  8. No clinician has reviewed this work. The specification is one reading of the instruction. Under What does a pass mean clinically? the rule’s doses are compared with one product label, and no patient’s treatment is assessed.

Conclusion

On the 30 released instances of MedAgentBench’s potassium task, the released grader gives the same score to a script that retrieves the patient’s most recent result and to a script that reads only the first page of a search. From the benchmark’s own records, 629 further instances that require the orders were derived. On these the first-page baseline passes 299 and the all-results baseline passes all 629.

With the server’s default sort order, the agent requested only the first page in 542 of the model’s 629 runs, and the model passed 255 under the relaxed grader. When the mock server listed the most recent results first, the model passed 521. On the first 200 instances, with the results list added to the task context, the model passed 195 of 200. In 369 of its 374 failed runs with the default sort order, the agent did not receive the patient’s most recent result. When asked to write the whole task as a program from the same tool definitions, instruction and context, the model wrote functions that read only the first page.

Given these results, the benchmark’s authors could make four changes to the task.

  1. Instances could be added on which the patient’s most recent result is on a later page and the dosing rule gives a different order for it than for the most recent result on the first page. From the existing records, 330 such instances that require the orders and 228 that require none can be derived.
  2. The tool definition could state the order and page size of a search, or the task could state that discovering them is part of what is tested.
  3. The grader could accept the route in the form the tool definition declares, and the task could state what the final answer must contain.
  4. The task could state whether the dose is a single dose or a daily total, and what an agent should do with a result that is not plausible. These two are questions for the benchmark’s clinical authors.

The model’s numbers come from one model, one run per instance in each condition, and a grader with two checks relaxed, so they cannot be used to rank the model against others. No language model is involved in the comparison of the first-page and all-results baselines: the two scripts, which differ only in whether they retrieve the patient’s most recent result, receive the same score on the 30 released instances and different scores on 330 of the 629 derived ones.

Glossary

Terms with a dotted underline in the text link here. On a screen with a pointer, the definition appears when the pointer rests on a term.

95% CI
A 95% confidence interval from a cluster bootstrap: the patients are resampled at random with replacement 4,000 times, and all of a drawn patient’s instances stay together. It expresses the uncertainty in the rate that comes from which patients are in the data. It does not include the variation between two runs on the same instance.
Action-required instance
An instance on which the two orders are required, because the patient’s most recent potassium result is below 3.5 mmol/L. On a no-action instance the most recent result is 3.5 or above and no order is required. The name no-action is taken from Mantravadi and coauthors.
All-results baseline
The first-page baseline with one change: its search requests up to 5,000 results in one page, which is the request the released grader itself sends. It therefore receives every potassium result the patient has.
Default sort order
The order in which the benchmark’s server lists results when a request does not set _sort: ascending record id. The order of record ids is not the order of effective time.
Derived instance
An instance built in this study from the benchmark’s records: one of the benchmark’s patients with only the potassium results that had been issued by a chosen earlier time, and with every time shifted by the same amount so that the chosen time equals the task’s clock. The instruction and the context are unchanged.
Effective time
The clinical time of a result, in the FHIR field effectiveDateTime. For a laboratory result it is usually the time the specimen was collected. On this page “most recent” means the latest effective time.
FHIR
Fast Healthcare Interoperability Resources, the standard interface of the benchmark’s record server. In FHIR a laboratory result is an Observation, a medication order is a MedicationRequest and an order for a test is a ServiceRequest.
Final
The FHIR status of a result that is complete. The other statuses include preliminary, amended, corrected and entered-in-error.
First-page baseline
A scripted baseline with no language model. It sends one search under the code K with no sorting and no page size, reads the one page that comes back, takes the result with the most recent effective time on that page, applies the dosing rule, and writes the orders in the form the released grader accepts. It never requests the next page.
Formal specification
The task’s instruction written in Lean as an exact condition. For any list of results and any clock time, exactly one outcome satisfies it. Where the text of the instruction does not determine the outcome, a choice was written into the specification, and each choice is listed on this page.
Instance
One test case: one patient’s record at one time, with the task’s instruction and context. The benchmark releases 30 instances of the potassium task.
Issued time
The time at which this version of a result was made available to clinicians, in FHIR’s field issued.
Lean
A programming language and proof checker. Lean accepts a theorem only when its kernel has checked every step of the proof.
LOINC
A standard coding system for laboratory tests. 2823-3 is the LOINC code for potassium in serum or plasma.
mEq
Milliequivalent, the unit in which potassium doses are written. For potassium, 1 mEq is 1 mmol.
Mock server
A program written for this study. It stores one patient’s potassium results in memory and responds to searches in the format of the benchmark’s server. It was used for the derived instances, because the benchmark’s server contains only each patient’s complete record.
Most recent first
The one change made in the second condition of this study: when a request does not set _sort, the mock server lists results in reverse chronological order of effective time, the order that a FHIR client requests with _sort=-date. The prompt, the tool definitions and the records are unchanged.
NDC
National Drug Code, the United States identifier for a medicinal product and pack size. 40032-917-01 is a bottle of 100 potassium chloride extended-release tablets of 20 mEq.
Null agent
A baseline that sends no request and finishes at once with an empty answer. The name is from Mantravadi and coauthors.
Page
One FHIR Bundle of a paged search: the results that one response to a search contains. On the benchmark’s server a page contains 20 results unless the request sets _count, and the response includes a link to the next page.
Potassium history
The potassium results that an instance contains for its patient. It is not the patient’s whole record: no other part of the record is used.
Reference implementation
A short Lean program that computes the outcome the specification requires. It is proved in Lean that its output meets the specification for every input.
Relaxed grader
The released grader, with its code unchanged, applied to a copy of a run in which two things have been changed: an oral route written as the object that the tool definition declares is rewritten as the plain string, and the final answer is replaced by an empty list, which removes it from scoring. Every other check in the grader still applies. The model’s runs on this page are scored with it, except the runs on tied instances and on instances with an added entered-in-error result, which are scored against the specification’s outcome.
Released grader
The Python function the benchmark’s authors wrote to score the potassium task, distributed in the file refsol.py. It reads the transcript of a run and returns pass or fail.
Round
One message from the agent and the response to it. The benchmark’s harness, the program that passes messages between the agent and the record server, ends a run after 8 rounds.
Run
One attempt on one instance through the benchmark’s protocol: at most 8 rounds, each of them a GET request, a POST request or FINISH.
Tied results
Two or three potassium results for one patient with the same effective time, which is the most recent in the patient’s history. Instances with tied results whose values differ are reported separately on this page.
Tool definition
The description of each permitted request that the benchmark gives the agent: its address, its parameters and their types.
Transcript
The complete record of a run: every message the agent sent and every response it received.
